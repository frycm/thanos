Compactor block splitting by series

Visual companion to the proposal 202609-compactor-block-splitting.md. Everything here is illustrative; sizes are examples.

1. Today: the biggest block gets frozen

The planner sums the index sizes of a plan's source blocks. When the running total reaches 85% of the limit it writes a no-compact-mark.json for the biggest block and replans without it. Two replicas of 30 GiB each sum to 60 GiB, so one is frozen even though the deduplicated result would be about 30 GiB.

B stays raw and overlapping forever. The marker survives a raised limit and must be removed by hand.

2. With splitting: one plan becomes M shard blocks

The planner decides the split. Once it has chosen a plan's sources, the split planner computes M from their metadata and names one output per shard in the plan: the group's labels plus __compactor_shard__ = "i_of_M", and the series partition. The executor knows nothing about shards; it runs one compaction pass per named output over the sources it downloaded once. Pass i keeps only the series whose hash modulo M is i-1. Step through it:

The planner selects the overlapping replicas A and B, exactly as today.
The split planner sums index bytes (and optionally series), divides by the per-shard target, rounds up, then up again to a power of two, and applies the lineage floor and the cap (section 3). It names one output per shard in the plan. M = 2 here; the picture shows M = 4.
The executor downloads and verifies the sources once. Nothing about this step changes.
One compaction pass runs per output over the same directories. Pass i uses the seam's PartitionedBlockPopulator, which filters each source's postings to the series of its partition and keeps only the symbols those series use. Merge and deduplication are the standard code. If the partitions together keep fewer series than the sources hold, which is what a changed --compact.block-split.ignore-labels looks like, the compactor halts before uploading anything.
Each output is a normal block: same time range, same resolution, group labels plus the shard label. All M record the full source set and the set of blocks the compaction produced. Series are disjoint across shards; replicas were deduplicated inside each shard.
Only after every upload succeeded are the sources marked for deletion. Independently of the marking, the shards supersede A and B only once the whole set is in the bucket: a crash after the first shard leaves the sources in place and the lone shard unpublished (section 6).

3. How the planner chooses M

M is not configured. Every stream starts unsplit, a plan splits only when its estimate demands it, and a shard group that outgrows the limits later splits again on its own. The estimate measures the sources, so for a shard group it measures that shard's data alone, and the count multiplies.

kparts the sources need: index bytes over 85% of --compact.block-max-index-size and, optionally, series over --compact.block-split.max-series, rounded up to a power of two Lthe sources' own shard count; 1 for unsplit sources Fthe finest count present in the lineage: any shard of the stream for unsplit sources, the finer shards of i_of_S for a shard group cap--compact.block-split.max-shards, rounded down to a power of two; 0 or 1 disables splitting refuseonly when the index needs a split and k_index × L exceeds the cap: the biggest block is marked no-compact with the existing reason, as today Mmax(min(max(k × L, F), cap), L); M = L means no split

If shard blocks of the lineage already span the plan's whole range, the plan is split into exactly those shards instead, whatever the estimate (section 7).

4. Which series goes where, and why re-splitting is free

Each square is one series, coloured by its shard. Move the slider to change M. Click a series to follow it: because M is always a power of two, a series in shard i_of_M can only land in i_of_2M or (i+M)_of_2M. That is why a shard group that grows too large can be split on its own, without reading any other shard.

1, 2, 4, 8, 16

Hashes here are synthetic. Real shards use labels.StableHash over the series labels stored in the block, without external labels, so the same series from two replicas hashes identically and is deduplicated inside its shard. Replica labels that live inside the series (HA pairs behind a receiver, agents over remote write) are left out of the hash with --compact.block-split.ignore-labels, so both replicas of a series share a shard. The ignored labels are part of a stream's lineage: set them before the first split and never change them.

5. Groups: the shard label does most of the work

The shard ID is an external label, so the grouper puts every shard in its own compaction group. The planner's overlap detection, vertical compaction and the store gateway's block sets work per group and need no shard awareness. A few places do have to know which shards hold which series, because all shards of a plan record the same sources: the metadata deduplication filter, the downsampling planner's coverage, and the split planner that keeps a stream's groups consistent.

6. Shards replace their sources only as a complete set

One shard's existence cannot prove that its sources have been replaced. Every shard records the set its compaction produced, and it supersedes anything only once every block of the set is present. A shard whose set is incomplete is unpublished: it supersedes nothing, and the compactor withholds it from its view so that it is never compacted on.

7. One stream over time

Fresh 2h blocks keep arriving in the unsplit group and compact to 2d as usual. When a plan exceeds the limit it splits, and its shards join the shard groups, which compact and downsample them like any other group.

The split planner keeps the unsplit group and the shard groups of one stream consistent:

8. Read path: unchanged, except one label is stripped

Shards are ordinary blocks. A query over a split range touches M blocks instead of one. Series are disjoint across shards, so no deduplication is involved. For every block that carries __compactor_shard__, the store gateway removes it from the series, label names and label values it returns, using the same mechanism it already uses to drop replica labels. The querier never sees the label.

With --selector.relabel-config on the shard label, shards 1 and 2 can live on one store gateway and 3 and 4 on another, which is the parallel fetch asked for in #5437. A compactor's selector must not separate them.

9. Distributed compactor: inherit first, fan out later

The plan names its outputs, so the manager's planner makes the split decision with its bucket-wide view, the task carries the outputs to the worker as data, the worker's executor produces exactly those, and the manager verifies every result block against one of the plan's outputs. None of it is shard-specific: one task, M passes, M outputs works as it is. The second step, drawn below, turns the M passes into M parallel tasks.

Future step. Sources and the plan's time envelope are reserved in the manager for the whole set, so the four tasks never conflict with other plans of the group. Completed shards are recorded in the journal; a failed shard is re-issued alone.

The one invariant. A shard block lists the full source set but holds a fraction of the series. Any logic that says "X supersedes or covers Y because sources(Y) ⊆ sources(X)" has to account for shards. The deduplication filter lets a shard supersede only its own lineage and only as a complete set; the downsampling planner, and the store resolution filter in PR #3, judge coverage per stream and shard: a block is covered through its own shard, a coarser one holding it, or finer shards that together hold all of it, never through another shard; the stuck-block fences of PR #2 hold per shard. Each has a regression test with shards of one plan.
