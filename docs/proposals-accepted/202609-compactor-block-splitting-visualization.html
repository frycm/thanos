Compactor block splitting by series

Visual companion to the proposal 202609-compactor-block-splitting.md. Everything here is illustrative; sizes are examples.

1. Today: the biggest block gets frozen

The planner sums the index sizes of a plan's source blocks. When the running total reaches 85% of the limit it writes a no-compact-mark.json for the biggest block and replans without it. Two replicas of 30 GiB each sum to 60 GiB, so one is frozen even though the deduplicated result would be about 30 GiB.

B stays raw and overlapping forever. The marker survives a raised limit and must be removed by hand.

2. Proposed: split one plan into M shard blocks

The executor computes M from the same estimate, then runs M compaction passes over the sources it downloaded once. Pass i keeps only the series whose StableHash(labels) mod M == i. Each output carries the external label __compactor_shard__ = "i_of_M". Step through it:

The planner selects the overlapping replicas A and B, exactly as today.
The executor sums index bytes (and optionally series). It divides by the per-shard target, rounds up, then up again to a power of two. M = 2 here; the picture shows M = 4.
Sources are downloaded and verified once. Nothing about this step changes.
M compaction passes run over the same directories. Pass i uses a populator that filters each source's postings to series with hash mod M == i, and keeps only the symbols those series use. Merge and deduplication are the standard code.
Each output is a normal block: same time range, same resolution, group labels plus the shard label. All M record the full source set. Series are disjoint across shards; replicas were deduplicated inside each shard.
Only after every upload succeeded are the sources marked for deletion. A crash before this point leaves the sources in place; a rerun's duplicates are removed by the existing dedup filter and garbage collection.

3. Which series goes where, and why re-splitting is free

Each square is one series, coloured by its shard. Move the slider to change M. Click a series to follow it: because M is always a power of two, a series in shard i_of_M can only land in i_of_2M or (i+M)_of_2M. That is why a shard group that grows too large can be split on its own, without reading any other shard.

Hashes here are synthetic. Real shards use labels.StableHash over the series labels stored in the block, without external labels, so the same series from two replicas hashes identically and is deduplicated inside its shard.

4. Groups: the shard label does the work

The shard ID is an external label, so the grouper puts every shard in its own compaction group. That is the whole trick: the planner, vertical compaction, the metadata dedup filter and the store gateway selector all work per group and need no shard awareness.

5. One stream over time

Fresh 2h blocks keep arriving in the unsplit group and compact to 2d as usual. When a 2d-to-14d plan exceeds the limit it splits, and its shards join the shard groups, where they compact horizontally with the previous 14d shards.

6. Read path: unchanged, except one label is stripped

Shards are ordinary blocks. A query over a split range touches M blocks instead of one. Series are disjoint across shards, so no deduplication is involved. The store gateway removes __compactor_shard__ from every series, label name and label value it returns, using the same mechanism it already uses to drop replica labels. The querier never sees the label.

With --selector.relabel-config on the shard label, shards 1 and 2 can live on one store gateway and 3 and 4 on another, which is the parallel fetch asked for in #5437.

7. Distributed compactor: inherit first, fan out later

A worker runs the same executor as the standalone compactor, so it inherits splitting as soon as it is in the shared code: one task, M passes, M outputs. The manager already verifies several same-range outputs; it only has to accept the shard label. The second step turns the M passes into M parallel tasks.

Sources and the plan's time envelope are reserved in the manager for the whole set, so the four tasks never conflict with other plans of the group. Completed shards are recorded in the journal; a failed shard is re-issued alone.

The one invariant. A shard block lists the full source set but holds a fraction of the series. Any logic that says "X supersedes Y because sources(Y) ⊆ sources(X)" is only correct between blocks with identical external labels. The dedup filter, the store resolution filter (PR #3) and the stuck-block fences (PR #2) all already scope that way; each gets a regression test with two shards of one plan.
